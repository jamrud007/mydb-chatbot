## Yang Dikerjakan

### 1. Buat script load test — `scripts/load_test_local.py`

Pendekatan: **async I/O (`httpx.AsyncClient` + `asyncio.gather` + `asyncio.Semaphore`)**, bukan thread-based (`requests` + `ThreadPoolExecutor`). Alasan performa:
- Async menghasilkan concurrency dengan overhead jauh lebih kecil dibanding spawn OS thread — satu event loop bisa menangani ratusan koneksi simultan tanpa context-switch overhead.
- `asyncio.Semaphore` membatasi concurrency secara presisi tanpa perlu pool thread terpisah.
- Cocok untuk mensimulasikan banyak client lokal dari mesin dev yang resourcenya terbatas.

Script menembak 3 endpoint tanpa auth (`/api/health`, `/api/metrics`, `/api/cache/stats`), mengukur wall time, throughput (req/s), dan latency (avg, p50/p95/p99, min/max) — format laporan selaras dengan gaya statistik yang sudah dipakai `MetricsCollector` (`utils/metrics.py`).

### 2. Jalankan server lokal + eksekusi load test

Server dijalankan via `python main.py` (Uvicorn, single worker, default thread pool). Karena Oracle DB (`192.168.1.50`) tidak terjangkau dari mesin dev, `chatbot` dan `metrics_collector` gagal init saat startup — endpoint `/api/metrics` dan `/api/cache/stats` konsisten mengembalikan `503 Service Unavailable` ("not initialized"), sementara `/api/health` tetap merespons (melaporkan status `unhealthy` dengan benar).

Ini sebenarnya hasil yang valid: server **tidak crash** di bawah 200 concurrent request meski dependency-nya down — exception handling & status check berjalan sesuai desain.

### 3. Uji bertingkat pada `/api/health` (satu-satunya endpoint yang benar-benar live)

| Concurrency | n | Wall time | Throughput | Avg latency | p50 / p95 / p99 |
|---|---|---|---|---|---|
| 10 | 300 | 1.20s | 250.0 req/s | 28.7 ms | 16.1 / 48.2 / 297.4 ms |
| 20 | 200 | 1.25s | 160.5 req/s | 83.8 ms | 51.1 / 325.2 / 331.4 ms |
| 50 | 300 | 2.28s | 131.6 req/s | **310.0 ms** | 292.9 / 387.6 / 397.6 ms |

## Hasil

### Temuan utama: latensi melonjak tajam di atas concurrency ~20

Dari concurrency 10 → 50, **avg latency naik ~10x (28.7ms → 310ms)** dan **throughput justru turun** (250 → 131 req/s). Ini bukan karena beban kerja endpoint (`/api/health` murni baca status in-memory, harusnya < 5ms), tapi karena:

- `health_check()` didefinisikan sebagai `def` (sync), sehingga FastAPI menjalankannya di **thread pool executor default** (`anyio`, kapasitas terbatas — biasanya ~40 thread).
- Uvicorn dijalankan **single worker** tanpa `workers=N` (`main.py:1003-1009`).
- Saat concurrency melebihi kapasitas thread pool, request mulai **mengantre**, sehingga p95/p99 ikut melonjak ke ~300-400ms — angka yang didominasi waktu tunggu, bukan waktu eksekusi.

### Implikasi untuk target demo (Minggu 8)

`docs/LATENCY_BASELINE_DAY14.md` menargetkan response cache HIT < 500ms. Dari hasil ini, **bottleneck di concurrency tinggi bukan di database/cache, tapi di lapisan server** (thread pool & worker count). Kalau demo melibatkan beberapa user mengakses bersamaan (misalnya > 20 request simultan), latensi bisa melonjak signifikan walau cache HIT — murni karena antrean di level Uvicorn/FastAPI.

### Rekomendasi (untuk dieksekusi di buffer day berikutnya, bukan sekarang)

1. Konversi endpoint baca-saja yang murni in-memory (`/api/health`, `/api/metrics`, `/api/cache/stats`) menjadi `async def` agar tidak menyita thread pool.
2. Pertimbangkan `uvicorn.run(..., workers=N)` atau jalankan via Gunicorn+Uvicorn worker untuk produksi (multi-process, memanfaatkan multi-core).
3. Re-run `scripts/load_test_local.py` setelah Day 16 (request_id middleware aktif) untuk membandingkan hasil dan men-trace request mana yang antre.
