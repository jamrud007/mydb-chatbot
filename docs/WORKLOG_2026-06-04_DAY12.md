# Worklog Day 12 — 4 Juni 2026

## Tujuan
Terapkan pagination/row limit konsisten di endpoint query dan review bottleneck query executor.

---

## Identifikasi Masalah / Topik Pekerjaan

**Topik 1 — Pagination/row limit tidak konsisten:**
- `QueryExecutor._add_limit()` sudah menambah `LIMIT`/`FETCH FIRST` ke SQL, tapi endpoint listing (`/api/results`, `/api/cache/entries`, `/api/suggestions`) menerima `limit` query param tanpa validasi batas atas — user bisa kirim `limit=99999`.
- `/api/results` tidak punya `offset`, sehingga tidak bisa dipakai sebagai paginator yang proper.
- Response `/api/results` tidak mengembalikan `total` (berapa entry tersedia), sehingga client tidak tahu ada berapa halaman.

**Topik 2 — Bottleneck review di QueryExecutor:**
- `DANGEROUS_PATTERNS` adalah list raw string. Setiap `validate_query()` call, Python memanggil `re.search()` yang mengkompilasi pattern dari awal — ini wasteful karena patterns tidak pernah berubah.
- `_add_limit()` menggunakan 4 `re.search()`/`re.sub()` inline yang juga dikompilasi setiap call.
- Timeout: dicek apakah `QUERY_TIMEOUT_SECONDS` dari Config benar-benar di-enforce — ternyata sudah ada di `db_connection.execute_query()` via `SET SESSION max_execution_time` (MySQL) dan `conn.call_timeout` (Oracle). Tidak ada gap di sini.

## Yang Dikerjakan

### 1. Precompile regex di `QueryExecutor` — `database/query_executor.py`

**Sebelum:** 11 pattern dikompilasi ulang setiap `validate_query()` call:
```python
DANGEROUS_PATTERNS = [r'\bDROP\b', r'\bDELETE\b', ...]
for pattern in self.DANGEROUS_PATTERNS:
    if re.search(pattern, query_upper, re.IGNORECASE):
        ...
```

**Sesudah:** Semua pattern dicompile sekali saat class di-load sebagai class-level attributes:
```python
_COMPILED_DANGEROUS = [re.compile(p, re.IGNORECASE) for p in [...]]
_RE_TOP_N      = re.compile(r'^(SELECT)\s+TOP\s+\d+\s+', re.IGNORECASE)
_RE_FETCH_FIRST = re.compile(r'\bFETCH\s+FIRST\b', re.IGNORECASE)
_RE_ROWNUM     = re.compile(r'\bROWNUM\b', re.IGNORECASE)
_RE_LIMIT_KW   = re.compile(r'\bLIMIT\b', re.IGNORECASE)
```

`validate_query()` sekarang memanggil `pattern.search(query_upper)` langsung (sudah compiled).
`_add_limit()` pakai `_RE_TOP_N.sub()`, `_RE_FETCH_FIRST.search()`, dll.

Regex compile terjadi sekali saat module diimport, bukan per request.

### 2. Tambah `offset` dan `total()` ke `ResultsCache` — `utils/results_cache.py`

`list_recent()` sebelumnya hanya support `limit`. Ditambahkan:
- Parameter `offset: int = 0` untuk skip N entry pertama.
- Method `total()` — return jumlah entry non-expired tanpa perlu mengambil semua data.

```python
def list_recent(self, limit: int = 10, offset: int = 0) -> List[...]:
    page = sorted_results[offset: offset + limit]
    ...

def total(self) -> int:
    self._cleanup_expired()
    return len(self.cache)
```

### 3. Update `ResultsListResponse` — `models/api_models.py`

Tambah field pagination ke response model:
```python
class ResultsListResponse(BaseModel):
    success: bool
    results: List[QueryResultSummary]
    count: int
    total: int = 0   # total entry tersedia (untuk hitung jumlah halaman)
    limit: int = 10  # limit yang digunakan
    offset: int = 0  # offset yang digunakan
```

Client sekarang bisa hitung jumlah halaman: `ceil(total / limit)`.

### 4. Tambah `Query(ge, le)` cap + offset di endpoint — `main.py`

Import `Query` dari `fastapi`.

| Endpoint | Sebelum | Sesudah |
|---|---|---|
| `GET /api/results` | `limit: int = 10` | `limit: Query(10, ge=1, le=200)` + `offset: Query(0, ge=0)` |
| `GET /api/cache/entries` | `limit: int = 50` | `limit: Query(50, ge=1, le=500)` |
| `GET /api/suggestions` | `limit: int = 10` | `limit: Query(10, ge=1, le=50)` |

FastAPI secara otomatis return `422 Unprocessable Entity` jika `limit` di luar range — tidak perlu validasi manual.

`GET /api/results` juga sekarang return `total`, `limit`, `offset` di response body.

## Hasil

**Bottleneck — QueryExecutor:**
- Regex compile terjadi 1x saat import, bukan per request. Pada workload tinggi (banyak concurrent user), ini eliminasi CPU overhead yang tidak perlu.
- Timeout sudah di-handle di layer `DatabaseConnection` — tidak ada gap.

**Pagination konsisten:**
- Semua endpoint listing sekarang punya batas atas yang di-enforce oleh FastAPI.
- `/api/results` kini proper paginator: client bisa iterasi dengan `offset` dan tahu kapan berhenti lewat `total`.
- Response schema terdokumentasi otomatis di `/docs` (Swagger UI) karena pakai `Query()`.

---

## Tidak Dilakukan (Scope Batas)

- Belum tambah `offset` ke `GET /api/cache/entries` — cache entries di backend (`CacheManager.list_entries()`) sudah punya `limit`, tapi offset belum ada. Bisa dilanjut di buffer day.
- Belum persistent pagination cursor (stateless offset — jika ada entry baru masuk saat user paginate, urutan bisa bergeser). Untuk skala ini masih acceptable.
- Analytics endpoints (`api/analytics.py`) tidak diubah — query mereka sudah aggregate (GROUP BY), hasil akhirnya kecil, jadi LIMIT dari QueryExecutor cukup.

## Catatan Teknis — Kenapa Precompile Regex Penting

Python `re.search(pattern_string, text)` selalu melalui langkah: parse pattern string → compile ke internal bytecode → match. Untuk string yang selalu sama, `re.compile()` memungkinkan langkah parse+compile terjadi sekali dan hasilnya di-cache di object. Meski Python punya internal LRU cache untuk 512 pattern terakhir (`re._cache`), eksplisit precompile lebih jelas dan menghindari risiko cache eviction saat ada banyak pattern berbeda di proses yang sama.

Dalam kasus `QueryExecutor`, setiap query yang masuk memanggil `validate_query()` (11 pattern) + `_add_limit()` (4 pattern) = 15 regex evaluasi per request. Dengan precompile, semuanya langsung ke step matching tanpa recompile.
