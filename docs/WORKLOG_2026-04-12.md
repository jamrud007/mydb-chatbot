## Identifikasi Masalah / Topik Pekerjaan

**Topik:** Tidak ada struktur folder yang mencerminkan arsitektur berlapis.

**Masalah yang ditemukan:**
1. `config.py` ada di root — tidak ada pemisahan antara "konfigurasi inti" dan "konfigurasi utilitas".
2. `utils/logger.py` dan `utils/structured_logger.py` diperlakukan sama dengan utilitas biasa, padahal logging adalah infrastruktur inti.
3. Tidak ada folder `core/`, `services/`, atau `repositories/` — semua kode rata di root atau di folder `utils/` yang terlalu luas.
4. Jika langsung dipindah tanpa shim, semua import lama di seluruh codebase akan rusak sekaligus.

**Pertanyaan yang dijawab hari ini:**
- Bagaimana memulai restructure tanpa mematikan sistem yang sedang berjalan?
- Di mana batas antara "infrastruktur inti" dan "utilitas"?

## Compatibility Strategy
- Import lama tetap valid (`from config import Config`, `from utils.logger import setup_logger`, `from utils.structured_logger import ...`).
- Refactor internal ke path baru dilakukan bertahap pada fase berikutnya untuk menghindari breakage.

## Penjelasan (Kenapa Day 1 Penting)

**Masalah sebelumnya:**
Semua konfigurasi dan logging tersebar langsung di `config.py` dan `utils/logger.py` di root.
Tidak ada pemisahan antara "infrastruktur inti" dan "utilitas biasa", sehingga sulit dikontrol
dependency-nya saat arsitektur berkembang.

**Yang diselesaikan:**
Memindahkan config dan logging ke `core/` sebagai *source of truth* — tapi **tanpa memecah kode lama**.
Caranya dengan compatibility shim: file lama (`config.py`, `utils/logger.py`) tetap ada,
tapi isinya hanya re-export dari `core/`.

```
Sebelum:          Sesudah:
config.py  ──►   config.py (shim) ──► core/config.py (source of truth)
utils/logger.py  utils/logger.py (shim) ──► core/logging.py
```

**Hasilnya:**
- Kode lama tidak rusak sama sekali (zero breakage).
- Modul baru bisa langsung import dari `core/` tanpa lewat path lama.
- Pondasi layer `core/`, `services/`, `repositories/` terbentuk.
